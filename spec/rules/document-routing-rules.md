# PromptHub 文档规则

本文件是文档投入、需求真源、计划及历史维护的唯一规则源。2026-09-09 起采用更新后的 Spec Init 风险分级方式；旧的五文件 change、七份测试说明、强制编号和逐阶段登记要求不再生效。

## 需要写多少

| 工作 | 最小文档投入 |
| --- | --- |
| 小修复、局部调整、普通重构 | 可以零文档；已有说明失真时原位更新 |
| 普通功能 | 更新已有主题；独立新主题至多新建一份权威说明 |
| 跨会话、多人或长期工作 | 按需保留一份计划，同一目标继续更新 |
| 数据、权限、公共契约、迁移、不可逆操作 | 在相关主题补设计、兼容、失败恢复和验收；重大独立决策才另写 ADR |

文档能指导安全实施和验收就停止扩写。不按改动文件数强制建 change，不强制 proposal/design/spec/tasks/implementation 五件套，不为一次需求铺满 workflow 目录或手工追踪矩阵。

## 一份主题，一份权威需求

先读 AGENTS、相关业务文档、匹配的活动计划和真实代码测试；只定位当前任务的边界。已有主题沿用原路径，入口指向它。新主题优先放在对应的 `spec/knowledge/` 领域；已有 `specs/<domain>/spec.md` 若仍是该主题权威则继续维护，无需搬迁。

用户确认需求变化后，立即原位替换权威文档中的旧要求和验收，未实现处标注“待实施”及差距。提议不能冒充已确认决定，代码现状不能覆盖已确认需求。其他文档中的需求副本改为引用；设计只补实现方案、取舍和差距。

不把代码/文档不一致本身当作重新确认的理由；先核对最新授权。只有尚未解决、会实质影响范围、安全、数据或兼容性的选择才需澄清。保护既有用户数据、脏工作区、进程及 Git/GUI 授权边界。

## 计划、验证和完成

计划只记动作、进度、阻塞、实际验证及剩余工作，并链接权威需求。可沿用 `spec/changes/active/<change-key>/tasks.md`，新计划可用 `plan.md`；不同时维护同一目标的两份计划或另一套验收定义。

验收直接关联测试路径、命令或人工步骤。测试先行、覆盖、安全、失败恢复和发布门禁仍按 [测试规则](testing-standards.md)、[存储规则](storage-evolution-rules.md) 和 [发布规则](../releases/release-rules.md) 执行。缺编号、一般格式或无关历史索引不阻塞实施。

完成标准是目标满足、必要验证完成或限制已说明、受影响约定准确。只同步本主题的权威说明、相关引用和状态。普通修改历史交给 Git；不为“无文档变化”创建记录。

完成范围及必要验收得到证据支持后，在同一次交付中把状态改为 `completed`，将整个 change 移到 `spec/changes/completed/<change-key>/`，更新引用并生成索引。`active/` 只保留尚需推进的工作；不能只改索引而把完成目录长期留在 active。旧的日期归档保留原位，不再复制进 completed。被替代且不再实施的方案标为 `superseded`，同样退出 active，并指向继任主题。

状态与发布、issue 关闭分别记录。范围内仍有实现、迁移或真实环境验收时，使用 `in progress`、`review-pending`、`needs-convergence` 或 `blocked` 并写清剩余条件；发布本身属于范围时才以发布结果作为完成条件。后续扩展不能把已完成范围重新标成未完成，除非原验收结论失效。

## 路径与兼容

- `spec/README.md`：任务入口，指向各主题，不复制需求。
- `spec/knowledge/{context,structure,behavior,reference}/`：按领域维护需求、设计、协议及必要参考。
- `spec/workflow/`：保留现有项目级入口，不要求每个需求更新六个阶段。
- `spec/changes/active/`：只有未完成的活动计划及尚未合并的既有主题。
- `spec/changes/completed/`：已完成或被替代的 change，全量保留原证据和 ID，入口链接现行主题。
- `spec/issues/`、`spec/releases/`、`spec/adr/`：真实问题、发布和重大决策，已有记录优先复用。
- `spec/changes/archive/`、`spec/changes/legacy/`、`spec/archive/`：历史证据，不能作为现行执行要求；由入口指向现行规则，无需批量重写历史。
- `docs/` 和根 README：用户及贡献者文档；Skill 模板不承载本仓库约束。
- `spec-init.topology.yml`：现有路径路由，不是必须创建的目录清单。

保留已被引用的 ID，不重新编号；新工作不默认要求 FR/DES/TEST/T。显式启用 `<!-- traceability: enforced -->` 的既有 change 继续检查自身关系。已有 issue/ADR 编号和历史名称保持兼容，不为普通主题新增全局流水号。

整理时只合并已确认重复的内容，保留独有约定与验证证据。移动或删除当前文档要修正其现行引用；历史入口明确旧路径失效。提交授权、原子提交、实际验证和 issue 关闭关联规则见 [提交规则](submission-traceability-rules.md)。

## 规则和设计的收敛

- 工程规则持续适用时保留在 `spec/rules/`；“落实完成”不等于规则失效。实施记录、迁移验证和被替代的规则正文移入 `spec/archive/rules/`，标明日期、终态及现行规则链接。当前规则文件只保留有效要求和必要说明。
- 大设计调整先找到同模块的权威主题，把最新确认的需求、设计决策、数据所有权和验收合并到该主题；未实现部分明确标注差距。活动计划只保留实施动作，不能成为另一份长期设计。
- 合并前核对独有要求、例外、迁移、回滚和验证证据；解决冲突后，旧设计进入 `spec/archive/designs/`，或随已完成 change 进入 `completed/`，并注明继任主题。禁止留下两份都声称“当前”的相反方案。
- 新决定生效时及时归档旧方案，不等待新方案全部实现；旧实现及数据的迁移保护继续遵循当前验收边界，归档文件不授权删除产品数据。
- 在本次交付结束前完成状态、位置、产品分类、现行引用和索引同步。运行 `pnpm spec:index` 后执行 `pnpm spec:test`，同时核对移动文件的链接。

## 产品分类

按责任产品分类，跨产品共享逻辑只有一个共享主题，各产品只记录自己的差异：

| Product | 所有权 |
| --- | --- |
| Shared | Core、DB、Shared 及跨产品领域合同 |
| Desktop | Electron 主进程、preload、renderer 和本机集成 |
| CLI | 独立命令行入口、交互与分发 |
| Web | 自托管服务、浏览器工作区及部署 |
| Cloudflare | Worker、D1/R2 bindings 与边缘部署 |
| Mobile | 移动应用、设备存储及原生验收 |
| Delivery | 发布、网站、工程验证及文档治理 |

活动记录在状态所有者文件中用 `## Product` 后的独立一行声明上述一个值；索引按该值分组。同一跨端计划归 Shared，正文列受影响产品，不复制多份计划。多个产品有独立生命周期时才拆分计划。稳定主题入口按产品导航；同模块共享规则只维护一次，产品特有设计不能混入别的产品正文。

历史流程验证见 [2026-09-09 迁移记录](../archive/rules/2026-09-09-document-routing-migration.md)。
