## 2. 问题与成因

- **现象**：升级 v0.5.9 前，把备份包（`*.phub.gz`/`*.phub`/`*.zip` 等）拖到 App 主窗口任意位置 → 全屏提示"释放以恢复备份" → 弹预览确认 → 恢复。升级后该能力消失，只能在「设置 → 备份与恢复」面板内拖拽。
- **根因**：v0.5.9 升级（`doc/v0.5.9.md` §4.2）时，我做剪裁判断认为上游 #135（设置页拖拽恢复）已覆盖 fork 定制（旧提交 `655abb1` 的 App.tsx 全局拖拽 ~198 行），丢弃了窗口级入口。判断错误：两者交互面不同，上游实现仅在设置页容器内响应拖放。

## 3. 修复方案

- **优化位置**：`apps/desktop/src/renderer/components/layout/BackupDropRestoreLayer.tsx`（新增 119 行）+ `App.tsx` 根层挂载（+5 行）+ `layout/index.ts` 导出。
- **调整方案**：不再搬运旧版自建的确认弹窗与恢复逻辑，而是做**纯入口层**——document 级 `dragenter/dragover/dragleave/drop` 四事件监听（带计数器防子元素抖动误触），识别备份文件后直接把 File 交给上游既有 `useBackupImportController.beginImportFromFile()`：预览计数、确认对话框、升级自动备份、`restoreFromFile`、成功 toast、页面 reload 全部走上游统一路径；确认弹窗已打开时（`importPreview` ref 防重入）不重复响应拖放。Web runtime 不挂载（与旧行为一致）。
- **文案**：overlay 两键 `app.dropToRestore` / `app.dropToRestoreHint` × 7 locale 全覆盖（旧版硬编码中文已按现行 i18n 规范改造）。
- **用户实际收益**：恢复"拖到哪都能恢复"的肌肉记忆路径；同时因复用统一控制器，比旧定制版多了**恢复前自动创建升级备份**保护（旧版直接 restore，无 createUpgradeBackup 步骤）与跳过大（skipped）明细 toast。
- **输入输出保证**：不改动设置页拖拽路径、不改动备份格式/IPC/DB；`BackupImportConfirmDialog` 与其控制器行为不变；`pickSupportedBackupFile` 复用上游函数（可接受的扩展名以 `BACKUP_IMPORT_ACCEPT` 统一口径，比旧定制版多支持 `.json`/`.gz`）。
